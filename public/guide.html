Type-by-type guide

10 types, 10 failure classes

Each card on the board runs a real check against the seeded shop. This page maps every card to the one fault only it can see — and to what all nine other cards are blind to.

Honest limits. The seeded faults are deliberately clean, one per class. Real bugs hide in the overlap — that's why the map matters more than the count.

Start here

What this demo proves

Run all ten cards on the seeded build: every card fails on exactly its own failure class and passes over the other nine. Then flip the suite toggle to strong — the mutation card is the only one whose verdict changes, because its subject is the suite itself, not the app.

The ten

Cards and their blind spots

Type 01

Unit

Exact-value asserts on pure functions. Catches the >-for->= boundary flip in shippingFee(100).

Blind to
anything that only exists between functions — mocks hide it.
Type 02

Integration

Wires real services together — no mocks. Catches addToCart writing basket while checkout reads cart.

Blind to
what users experience across screens; the parts work, the journey breaks.
Type 03

E2E

Drives the composed flow — signup → pay → confirm. Catches the page that reads confirmationId when payment stored orderId.

Blind to
load, drift, and markup changes that keep the flow working.
Type 04

Snapshot

Diffs rendered markup against a recorded baseline. Catches badge-success renamed to badge-ok.

Blind to
logic — a snapshot can't tell right output from wrong output.
Type 05

Contract

Compares the keys the consumer reads against the payload the provider actually sends. Catches totalCents → total_cents.

Blind to
everything inside each service — shape drift is its whole world.
Type 06

Load

Counts work at scale: 200 products × 400 queries. Catches the O(n×m) scan that was instant at 20 items.

Blind to
correctness — a fast wrong answer passes every time.
Type 07

Chaos

Kills the dependency mid-call. Catches the recommendations call with no timeout and no fallback — the request hangs forever.

Blind to
failures that need a healthy dependency to exist.
Type 08

Mutation

The meta-type. Runs real mutants (>=→>, doubled fee, skipped discount) against the suite and counts survivors.

Blind to
the app — its subject is the tests themselves.
Type 09

Smoke

Cold-boots the app and pings health. Catches the throw at module init — unit tests import functions and never boot.

Blind to
every behavior; it only asks "does it start?"
Type 10

Regression

The pinned test written when incident #4821 was fixed. Catches cartTotal([]) returning NaN — again.

Blind to
new bugs — it only guards failures that already happened.

Run locally

Inspect the evidence

npm test         # bug manifestation + runner matrix + server
npm run board    # CLI: 10 types × 10 bugs caught/missed matrix
npm run check    # both
npm start        # serve the lab on :3000

Try node scripts/board.mjs --fixed to watch every card go green — same suite count, different map.

Limits

What this demo does not claim

  • Seeded faults are clean and orthogonal; real bugs overlap classes.
  • "Load" measures operation counts, not wall-clock latency or percentiles.
  • "Chaos" simulates one dead dependency, not a fault-injection platform.
  • Three mutants demonstrate the idea; real mutation testing generates hundreds.
  • A pass means "this class is covered", never "the system is correct".
